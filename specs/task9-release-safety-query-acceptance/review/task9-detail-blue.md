## Findings

DB1 | `decision-log.md:609`（D-002）、`:633`（D-004）、`:107`（验收标准场景）、`:112`（AC-K3-1）| **新版本的内容组成没有定义**：D-002 只说「把当前版本整份放入 LKG，把新内容复制/校验到暂存区」，D-004 说「把批次内容按既有目录/命名规范合并进该库」。到底新版 = 库内原有内容 + 本批内容（+ 重生成的 Home/Index），还是 = 只有本批内容？没说。这直接决定两件事：① 首次发布到一个**非空**的既有知识库时会整库替换、把用户原有页面全部删掉（与核心需求「基于某一个已存在的知识库…直接消化合并」正相反）；② AC-K3-1 的「新版 tree hash」无法计算，负例断言没有对照值。同名路径碰撞（本批页 vs 库内既有托管页/手写页）也没有胜负规则 | spec 必须先冻结一条合并规则并写进 AC：新版 = 库内既有内容（未被本批声明的路径原样保留、不删除）+ 本批声明路径的新内容 + 确定性重生成的结构页；同名路径按 `managed_by: KnowledgeDigest` 标记决定覆盖（托管页可更新，非托管页=硬失败并列出冲突清单）；先在 staging 里算出「新版预测 tree hash」写入发布记录，AC-K3-1 用它与旧版 tree hash 做二选一断言。

DB2 | `:113`（AC-K3-2）、`:647`（D-005）、`:141`（NG-011）、`:784`（m3 处置）| AC-K3-2 的失败注入点在本卡范围内可能**真空满足**：NG-011/纠正确认「发布与验收不调 LLM」，于是发布命令失败时 `provider_calls=0`、`provider_tokens=0`，带上 `no_provider_call_yet`/`provider_unavailable` 就合法——三项非 null 成立，但母任务 F-002 要修的「两次失败运行约 300 次 provider 调用无账」在这条链路上根本没被度量。另外 D-005 说「`publisher.py:113` 的硬编码 null 必须消除」，但 D-010 已决定不复用 `publisher.commit`，该缺陷是否仍会进入本卡可达路径未写明；`elapsed_ms` 也没说是发布耗时还是编译+发布总耗时 | spec 明确：①发布命令读入所发批次的 `_audit/run-metrics.json`，把该次编译的 `provider_calls/provider_tokens/elapsed_ms` 连同自身 elapsed 一并写进发布 run 记录（承继字段与本地字段分开命名）；②AC-K3-2 的验收用「编译+发布同一次运行」构造失败（例如让 finalize/发布阶段在编译已花调用之后失败），断言承继的三项等于编译侧实际值且非 null，禁止用 provider 为 0 的纯发布失败充数；③`publisher.py:113` 的修复若不在本卡可达路径，就在 spec 记为「随 K4 删除或同批修复」并说明理由。

DB3 | `:114`（AC-K3-3）、`:673`（D-007）、`:804`（OPEN-K3-4）| 汇总规则仍不可执行：「对照未覆盖不计入我方优势」+「任一硬失败题即整体失败」只定义了**必要条件**，没有定义①什么叫「硬失败题」；②通过需要满足什么（若 20 题里 15 题查不到答案但都不是「硬失败」，是否算通过？）；③「对照未覆盖」到底算不算失败（S8 只说不得计为我方优势，未说不通过）。反例：自动生成的 20 题全部是「X 是什么」，坏产物只保留标题即让 18 题「对照未覆盖」且无硬失败 → 汇总判通过，FR-K3-4 要防的「全过」换个形式回来了 | spec 把汇总写成唯一可执行形式并给样例：冻结 `硬失败题 = {答案命中=false 且 出处正确=false}`、`对照未覆盖` 单独计数、`通过 = 硬失败数=0 且 (答案命中数 / (总题数 − 对照未覆盖数)) ≥ 冻结阈值`（阈值数值与「对照未覆盖」占比上限一并冻结）；同时在 AC-K3-4 里要求坏样本上至少 N 题被判失败。

DB4 | `:258-273`（OI-03）、`:548`（取证一 #1b）、`:102`（已选方向落点选择）、`:219-222`（Fixed categories）、`:466-480`（OI-14）、`:421-434`（OI-16）| **承载记录与 D\* 相互矛盾**：OI-03 仍写着「`atomic_release` 已具备…保留旧版…可作为落点（复用/改造而非从零实现）」，而 D-010 已决定不复用其入口与完整包判据，D-002 已改为自建 LKG 指针；取证一 #1b 仍写「**支持保留旧版**（旧版只移入 rollback 不删）」，这正是 B1 的误判源头（实际是随机名残留、不清理、无指针）。同时 OI-06/07/08/09/10/12/14/16 仍是 `status: open`、disposition 写着「待 grill / 待 R3」，但 grill 与 Talk R3 已发生且 D-006/7/8/9/11 已写死；OI-14 还写着「待 direction-advice 后重新裁决，不得静默采纳」，而用户已在 R3-Q4 裁决维持 C | 决策草稿定稿前把 OI 记录与 D\* 同步：OI-03/OI-14/OI-16 等改为 confirmed 并引用对应 D 编号；把取证一 #1b 更正为「旧版留在随机名 `.task3-rollback-<uuid>` 且成功路径不删除、无指针，故不可用作回滚来源」；`## 已选方向` 的「复用/改造 atomic_release」一句改为与 D-010 一致的「只借鉴锁内两次替换与失败自动恢复的机械」。否则 build-spec 读到哪一份都可能得出相反结论。

DB5 | `:609`（D-002）、`:697`（D-009）、`:794`（RISK-K3-3）| LKG 状态机只写了一半，缺四种状态：①**没有 LKG 时执行回滚**（首次发布后、或上一次发布前库为空）应明确 blocked 而不是静默 no-op；②**指针与 LKG 内容对不上**（被手改/损坏）应 blocked 并列出冲突，不得换回一个未知版本；③**回滚成功之后 LKG 里应是什么**（被换下的那一版？留作可回滚前进？）没说，会导致「回滚一次后还能不能再回滚」不可判定；④指针写入与 LKG 复制的**顺序与持久化**（先写指针还是先备内容；无 fsync 时掉电会得到指针指向半份 LKG）。另外「库级写锁」的落点未定：`kb_lock` 在传入目录内建锁文件，若锁文件落在被换版的那个根目录里，换版会把锁文件一起搬走 | spec 补一张 LKG 状态/转移表（空 LKG、有效 LKG+指针一致、指针不一致、回滚成功、回滚失败、轮换）+ 各态的机读 reason；明确「锁目录 = 目标库的父目录（锁文件不进入被换版的根）」；明确指针先于 LKG 内容落盘的顺序与 fsync 范围（可与 DB10 合并写）。

DB6 | `:666`（D-006 补充）、`:114`（AC-K3-3）、`:167`（J8）| 验收与被验收目录之间存在**竞态**且没有前置条件：验收命令要从活的「指定知识库目录」取 tree hash，而发布/回滚随时可以换版（G-1 还允许一个短暂缺失窗口）。反例：验收在两次 `os.replace` 之间取指纹，得到「目录不存在」或半份内容，随后逐题判定与重放全部建立在一个不存在的版本上；或验收中途发生一次发布，前半段读旧版后半段读新版 | spec 写死验收前置：验收命令先取与发布同一把库级锁（拿不到即 blocked「有发布在进行中」），在锁内一次性算出并冻结被验收树指纹与逐文件清单，之后只对冻结清单做逐题判定；重放时若目标目录 hash 与记录不一致，按 D-006 报「被测对象已变，不可复跑」。

DB7 | `:633`（D-004「按既有目录/命名规范合并」）、`:697`（D-009 整根断言）| 「合并」会重写库级结构页（Home/Index/分类页），但**证据型页面不得被重写**这一点没冻结。K1 的 claim 级锚点/出处是 AC-K3-3「定位有效/出处正确」的唯一依据，如果发布为了适配目标库而重新渲染页面（改 frontmatter、重排、重写相对链接），锚点与行区间会漂移，判定器要么误判要么无从判定；而整根 tree hash 断言也分不清「哪些文件允许被发布改写」 | spec 列出发布允许写入/改写的白名单（结构页与索引页）与**逐字节复制**清单（`products/**` 页面与 `_audit/**` 证据文件），并在发布记收里记录「复制文件的源 sha256 = 目标 sha256」断言；AC-K3-1 的整根断言加一条：白名单以外文件字节不变或按合并规则确定性生成。

DB8 | `:723`（D-011）、`:749`（D-013）、`:160`（J1）| ①发布记录**放哪、怎么被找到**没写：D-011 说 `released` 由「K3 自己的发布记录」承载、不回写 K1 manifest，但没定位置。反例：半年后打开知识库目录，无法回答「这批页面是哪次批次、哪次发布产生」，也无法把库内页面追回到 `attempt_id`；②首次发布到空目录时「按新库建立默认骨架」的骨架内容与允许写路径（`kb.structure.md`）由谁生成、是否参与整根断言，未定；③J1 的「目录不是知识库形态且不允许新建：明确拒绝」里「不允许新建」的判定条件未定 | spec 冻结：发布记录落在目标库根内固定路径（例如 `_digest_release/releases/<release_id>/release.json`），内容含 batch `attempt_id` + batch manifest hash + 旧版 tree hash + 新版 tree hash + LKG 指针 + 本次 run 成本三项；新库骨架用 `kb_structure.default_publication_structure()` 生成并登记其 sha256；「允许新建」的判定写成显式规则（目录不存在 或 存在且为空 ⇒ 建骨架；存在且非空 且 无 `kb.structure.md` ⇒ 拒绝）。

DB9 | `:685`（D-008）、`:805`（OPEN-K3-5）| 坏样本与题目之间**没有绑定关系**，AC-K3-4 不可机器检查：三类坏样本（缺表格 / 错出处 / 孤儿页）是页面级缺陷，而判定是逐题四结果。反例：把「缺表格」的坏产物跑一遍问题集，若题集里没有一道题需要表格才能答，则坏产物照样全过，「能查到坏产物」这条验证失败却看不出原因；反过来也可能因为一道无关题的误判而假阳性 | spec 要求坏样本 fixture 里给每类缺陷绑定至少 2 道「必须判失败」的题目 + 期望失败原因（例如「答案命中=false，因表格缺失」），并冻结 fixture 的 sha256；AC-K3-4 的通过条件写成「三类样本各自的绑定题全部判失败，且正确产物上这些题不判失败」。

## 总结（≤500 字）

方向层已明显收敛：我上轮的 B1/B2/B3 与 M1–M6 都有对应处置（D-002/D-005/D-006/D-007/D-008/D-010/D-011 + 审查处置表），主干可以进 build-spec。但有两处会直接影响 AC 是否成立。

**blocking：DB1、DB2。**

- DB1：新版本到底由什么组成没定义。D-002/D-004 说「合并」，却没说新版 = 库内原有内容 + 本批内容（+ 重生成结构页）还是只有本批内容。若按字面「整库换版 + 只把新内容放进暂存区」，首次发布到一个非空既有库会把用户原有页面整库删掉，与核心需求「基于已存在的知识库合并」相反；同时 AC-K3-1 的「新版 tree hash」根本算不出来，负例断言失去对照值。
- DB2：AC-K3-2 可能真空满足。本卡已确认发布/验收不调 LLM（NG-011），发布失败时调用数天然为 0，带上 reason 就合法，而 F-002 要修的「300 次调用无账」发生在这条链路之外，等于没测到；`publisher.py:113` 的修复是否仍在可达路径也没写。

**major 里最需要 spec 前写死的：** DB4（OI-03 与取证一 #1b 仍写着「atomic_release 保留旧版可复用」，与 D-002/D-010 相反，会误导 build-spec）、DB3（汇总规则只有必要条件，缺「硬失败题」定义与通过阈值）、DB5（LKG 缺无指针/指针损坏/回滚后再回滚三态，锁目录未定）、DB6（验收与发布并发，指纹可能取到缺失窗口）、DB7（合并会重写结构页，须冻结证据页逐字节复制）。

其余 minor（DB8 发布记录位置与骨架、DB9 坏样本与题目绑定、DB10 崩溃级口径未写进 AC、DB11 三种输入态、DB12 89 份排除规则与偏离声明）可在 spec 一并冻结。
