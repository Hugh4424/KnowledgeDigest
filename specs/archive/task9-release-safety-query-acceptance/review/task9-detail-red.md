## 总结（≤500 字）

**blocking：N-1、N-2、N-3、N-4。** 用户纠正本身是对的（F-2 真实收敛），F-3/F-5/F-6 也确有实质改动；但 F-1、F-4、F-7 属于"记了账没解决"，且新引入了三处硬冲突。

1. **N-1 最致命**：G-1=A 接受目录短暂缺失，AC-K3-1 与 OI-16 反例又要求"不存在第三种状态/不可读即失败"——同一文件四句话互相打架。按 G-1 实现必然过不了 AC；要过就只能让测试绕开它本该覆盖的窗口，AC-K3-1 因此真空。必须先决定设计（稳定入口/指针，还是接受并有界记录缺失）。
2. **N-2/N-4 是"没写死就等于没定"**：LKG 固定槽位放哪、发布失败收据写哪，两种位置各自撞 D-013 只写边界、tree hash 断言、D-011 不改 K1 产物；不写死就会在 build 阶段被随机选一个，把 AC 打穿。
3. **N-3 说明 F-7 是文字处置**：发布/验收零 provider 调用（NG-011），三项成本恒为 0+reason，AC-K3-2 可真空通过；真正的 `observed_calls=null` 在 NG-003 禁止触碰的编译链路，而 D-005 点名的 `publisher.py:113` 因 D-010 不复用 `commit` 已成死代码。要么扩权修复编译失败记账，要么诚实降级 AC 并撤回该承诺。

其余 major 里，N-6（无 LLM 时"答案命中"退化为词面匹配 + 坏样本未冻结 → AC-K3-4 不可执行）与 N-8（无台账/额度 + 必须先真跑一次编译 → 范围失控）是本轮新增的两个真正风险点；N-7（ADR-0013 未修订）会让下一个 agent 拿到互相矛盾的权威。

建议：N-1/N-2/N-3/N-4 在写 spec 前由用户再裁决一次（都是"二选一"性质，不是补文案）；N-6/N-8 作为 AC 前置写死。
