# KnowledgeDigest 知识发布架构盲审

## 结论（不超过 8 条）

1. **诊断大方向正确**："保存层完成、知识产品层未完成"的判断有充分硬证据支撑（85/86 单来源主题、`product_slug=0`、58/120 占位 Summary、120/120 空 Related topics、31 条 provider 失败仍进正式页）。这不是模型换型或改文件名能解决的问题。
2. **"按主题编译成产品/模块/场景/规则/技术/经验页面"必须是核心**，这是 CompanyBrain 可读的根因，也是 Task2 完全缺失的一层。任何不触碰正文编译的修复都是表面修补。
3. **当前修复方向（新增 Knowledge Compiler 层）架构上正确**，但存在过度设计风险：实体/本体模型过重、页面类型一次定义 8 种、`TopicPlan` 全量规划与增量 digest 的拍板前提存在未解决的张力。
4. **优先级有错位**：交付包拆分（审计包/知识包分离）和失败降级治理是低成本的确定收益，被排在任务 C；而本体设计被放在任务 A 最前，属于风险最高、最容易空转的部分。
5. **原始方案已实现的部分比报告承认的略多**（S5/S6、防丢失 9 条大多落地），但 S3 的 LLM 路径判定、S4 的提炼合并（`old_target_body` 从未填充）确实只有规则/拼接壳，报告的"只实现保存/溯源"判断成立。
6. **缺失一个关键议题：增量语义**。原始方案拍板"增量执行、不全量重建"，而 TopicPlan 全量规划暗示全量重编译；二者如何调和（局部重编译 vs 全局主题漂移）报告没有回答。
7. **验收合同是全套材料中最有价值的产出**，应保留并前置：20 个真实读者任务 + human_reviewed 分级 + "不过门禁只能叫 candidate"是真正的质量杠杆。
8. **总纲冲突未承认**：原始方案最高优先级是"技能要尽可能简单"，新方案叠加实体/本体/生命周期后复杂度显著上升，修复报告没有给出复杂度预算或裁剪原则，有重蹈"调研完整但质量合同缺位"的风险——只是这次换成了"合同完整但实现过重"。

## 根因证据

**根因（结构性）**：

- **主题粒度由传输边界决定**：`_digest/batch-state.json` 记录 `batch_size: 1`、89 批次；86 个簇中 85 个单来源且全部判 `auto`（单来源簇 `min_pair=1.0` 天然过阈值）。聚类 ID 被直接用作 `topic_id`（来源集合哈希），批次边界变成了知识边界。
- **生成职责被合同禁止**：`llm.py` 的 `publication_only` prompt 明确禁止模型返回 `final_body`；Task2 运行 `llm_summary_enabled: false`。模型只产元数据，正文=原始 Evidence 按 300 行切片。这是"正文不可读"的直接技术根因，不是模型质量问题。
- **S3 路由是词面阈值**：`len(selected)` 规则决定 new/revise/merge_multiple，原设计要求的 LLM 判定、F1–F7 多特征均未落地；jina 探测失败后整次回退 Jaccard，进一步弱化语义。
- **无实体层**：`topic-index.json` 中 `product_slug` 非空为 0，EMM/AE/iOS/GoInsight 混在同一 51 页叶目录。

**表面症状（易被误当根因）**：hash 文件名（27 个 `topic-<hex>`+24 个 hash 后缀）、300 行分页、"来源未说明"占位文本、Summary 英文、13 个空分类页。这些都是上游结构缺失的投影，单独修任何一个都不会改变读者体验。

**治理层根因**：质量门只查"有没有"（Claim 数、行数、链接、指纹），不查"能不能回答"；`written` 状态掩盖 `quality.status` 全空；17 个 `agent_assisted_review` 样本被展示为对比结果而人工确认仍开放。

## 原方案实现缺口

对照 original-design.md：

**已实现（且实现得不差）**：S1 读取/指纹/空壳门禁/快照；S2 complete-linkage 形态与双阈值分层；S3 top-k 与三路 action 的规则路径；S5 临时文件+fsync+原子 rename+写前归档+路径安全（设计明确删除 CAS/journal，不算缺口）；S6 claim 级 source_uri/定位/指纹/replay；防丢失 9 条中约 6 条落地。

**只实现保存/溯源、未实现发布质量**：

1. S3 设计写明由 LLM 判定路径，实现无任何 LLM 调用——规则阈值是正式主路径而非降级路径。
2. S4"提炼合并"名存实亡：`old_target_body` 在 pipeline 中从未填充，revise/merge 实际是历史 Claim 拼接而非理解后重写；`remove_with_reason` 无真实数据协议，只处理 `unsupported:` 前缀。
3. `max_doc_lines` 拆分被实现为 300 行硬切（`page_layout.py` 忽略传入参数），拆分是行数安全阀而非业务重组——恰好违背原设计"重组而非丢弃"的意图：虽然没丢内容，但也没重组。
4. F1–F7 多特征决策未落地，S2 只有一个相似度分数，且不读既有 KB。
5. 非文本引用只是正则 URL 列表，无附件/截图/父子页一等模型；表格保留原文但未语义化。
6. 原设计的 Phase 验收（fixture、空壳、超长文档）天然覆盖不了读者质量——这是方案层的合同缺口，Task2 后补的 reader 指标也未设为停止门。

## 对当前修复方向的批评

**正确应予保留的**：两层架构（保真层/编译层）；raw→candidate→formal 状态机；Evidence 退居证据区；失败来源不进 formal 导航；human_reviewed 与 agent_assisted 严格区分；三项任务拆分而非一个大重构。

**遗漏**：

1. **增量语义未解决**：原拍板是 `digest(new_dir, kb_dir)` 增量执行；全量 TopicPlan 规划要求看到全语料。新增一篇来源时，主题边界、产品归属、Related topics 如何局部更新而不引发全局重编译？这是该架构能否长期存活的关键问题，报告完全未提。
2. **账本一致性问题未纳入修复范围**：provenance 审计报告给出 4,904 vs 4,756 不闭合、`duplicates.jsonl` 非幂等、source-index/snapshot/batch 三方来源集合不一致、89 批全 `succeeded` 掩盖失败——这些保真层缺陷在"保留 S1–S6"的措辞下被默认合格，但它们是质量门误报的直接来源，应列入任务 C 的硬门。
3. **S6 审计顺序缺陷**：`audit_provenance()` 在 writeback 之后执行，fail-closed 方向反了；source-index 在事务外被单独覆盖。这是保真层自身的合同缺口，"保留"不能等于"不动"。
4. **Confluence 输入特征研究仍缺**：父子页、截图、双语、表格、版本页在本批 89 篇中的分布没有量化，编译器的结构归一规则缺少输入依据——这正是上一轮"调研没翻译成合同"的同类风险。
5. **研究可复现性**：原始方案以 host-path fixture 引用外部调研、无版本/hash 绑定，修复报告指出了这一点但自己的方案（本体从 CompanyBrain 提取）同样依赖外部参照物，未给出固化方式。

**过度设计**：

1. `KnowledgeEntity` 一次定义领域/产品/模块/业务对象/角色/场景/版本/边界/别名/置信度十个维度——89 篇语料、实际只涉及有限几个产品，实体模型应只保留产品/模块/别名/边界四项起步。
2. 8 种页面类型一次铺开过多；本批语料实际需要的主要是操作/规则、产品/模块总览、部署/技术三类加"经验"。
3. `ReviewState` 四态 + 五种 needs_review 原因，对"手动触发、单人重跑"的拍板场景偏重；raw/candidate/formal 三态足够，原因用自由字段记录即可。

**错误优先级**：交付包拆分（279MB 中正文仅 4.9MB，读者首先看到工程现场）和"失败页退出 formal 导航"是几天级工作量、确定收益，却排在任务 C；本体设计是风险最高项却排最前。建议把"读者可见面治理"提前为独立的第一批快赢。

## 建议的最小可行修复架构

保留两层划分，但把编译层压到最小：

```text
[保真层 S1–S6 原样保留]
  修补：S6 审计移到写回前；账本去重与三方来源对账；
        duplicates.jsonl 幂等；batch status 与 claim status 分离。

[编译层（新增，只有一个核心产物）]
  全量来源清单（跨批次，批次仅作 provider 传输）
  → 结构归一：标题层级/表格/FAQ/双语/截图引用标记，噪声打分
  → 主题归并：以"产品词典 + 来源路径 + H1 + 相似度"做多特征归并，
    单来源可以成为一个主题，但必须经过"是否可与既有主题合并"的显式判定
  → 页面规划：每主题选一个页面类型（首期 4 种：总览/操作规则/技术部署/经验）
  → 正文编译：LLM 生成类型化 sections，每段绑定 Claim；
    编译失败 → 该主题只发 raw 档案页（明确标注"未经编译的原文"），
    不进 formal 导航，不写占位 Summary
  → 读者验收门 → 正式发布
```

关键简化决策：

- **本体 = 一份可审计的产品/模块词典**（类似 CompanyBrain `module_rules.json` 的做法），不是十维实体模型。词典人工可改、版本化、低置信命中进 review。
- **稳定 ID 与可读路径分离**：hash 只留在 frontmatter 的 topic_id；文件路径由"产品/模块/语义标题"生成，冲突显式报错而非加 hash 后缀。
- **批次只是传输**：TopicPlan 对全量来源清单计算，provider 调用分批，主题成员资格不受批次影响。
- **交付物分包**：读者包只含 Home/indexes/pages/source-index；`_digest`/`_archive`/队列/对比报告进独立审计包。

**回答审查目标 5 的核心判断**：是的，"来源按主题编译成产品/模块/场景/规则/技术/经验页面"必须作为核心——它是 Task2 与 CompanyBrain 之间唯一的本质差距；其余（命名、分页、索引）都是它的下游。防复发机制：批次不作主题边界（TopicPlan 全量计算）、单来源不自动成主题（强制合并判定）、hash 不进路径（合同校验）、Evidence 不作正文（类型化模板渲染，Evidence 只在页尾）、LLM 失败降级为 raw 档案页而非占位 formal 页（状态机强制）。

## 任务拆分与顺序

建议改为四项，按"读者可见收益/风险"排序：

1. **任务 0（快赢，1 量级）**：交付包拆分；失败/占位页移出 formal 导航（进 raw 区并在 Home 可见）；修复空 Provenance 页、账本对账、S6 审计顺序、source-index 链接化。不改生成逻辑。
2. **任务 A（合同）**：产品/模块词典 v1（只从本批 89 篇提取）；4 种页面类型模板；raw/candidate/formal 状态定义；20 个固定读者任务与人工评分表；增量重编译规则（新来源如何触发局部主题更新）。
3. **任务 B（编译器 + 小语料验证）**：12–20 篇代表语料上跑通"归一→归并→规划→编译→验收"；每个编译段必须回指 Claim；失败只发 raw。完成标准：固定问题集在样本上可答，人工归因准确率 ≥90%。
4. **任务 C（全量 + 门禁）**：冻结词典/模板/输入 manifest 后全量运行；同套 20 题对比 Task2、CompanyBrain 与新结果；machine/assist/human 三级验收全绿才算发布。

## 硬质量门禁

机器底线（保留）：Claim 无损可回指、路径安全、无断链、原子/归档写、账本三方对账闭合、duplicates 幂等。

读者硬门（新增，任一不过则只能标 candidate）：

1. 20 个固定真实问题全部有入口，Home 到答案 ≤4 跳。
2. formal 页零占位：不出现"请阅读 Evidence""来源未说明"式文本；缺事实的字段省略而非占位。
3. 标题脱离路径可理解（人工理解度 ≥90%）；formal 路径无 hash、无 `part-N` 作为主入口（分页必须有主题总览页 + 上下页导航）。
4. 产品/模块归属人工准确率 ≥90%，不确定进 review。
5. 正文按页面类型含必备 sections（用途/步骤或规则/边界/版本/来源）；Evidence 不作正文。
6. provider 失败、事实冲突、无正文来源零进入 formal 导航；其状态在读者入口可见。
7. Related topics 不允许全库同一占位：要么有真实链接（可审计依据），要么字段省略。
8. 验收报告三分级：machine_pass / agent_assisted / human_reviewed 不得互相冒充；human_reviewed 未通过不发布。
9. 读者包体积与文件数有预算：读者目录不含 run/archive 现场。

## 最危险的三条误区

1. **把词典/本体当成果而不是把编译当成果**：任务 A 最容易产出一份漂亮但无执行力的本体文档（重蹈"调研完整、合同缺位"）。判断标准只有一个：样本语料经编译后，固定问题集能不能被真实读者答出来。本体是为编译服务的副产品，不是交付物。
2. **"保留 S1–S6"被误读为"S1–S6 无缺陷"**：账本不闭合、审计顺序倒挂、批次状态误报就在保真层内部；若原样保留，新架构的质量门仍会撒谎。保真层需要一轮对账与 fail-closed 顺序修补，这不违背"不重写"原则。
3. **用降级路径冒充完成态**：本轮事故的本质就是 fallback 占位页进了 formal 导航、agent_assisted 被当成人工通过、`written` 被当成质量通过。新架构若允许任何"为了不断流而降级"的产物进入正式面（哪怕带着更优雅的状态标签），三年内会再次产出"机器全绿、读者弃用"的知识库。降级的唯一合法出口是 raw 区 + 可见的待审队列。
