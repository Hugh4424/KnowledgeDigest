# 原始方案 S4–S6 实现审计

审计对象：

- 原始方案：`docs/plans/universal-knowledge-digest-design.md`
- 实现：`src/knowledge_digest/draft.py`、`page_layout.py`、`writeback.py`、`provenance.py`、`pipeline.py`、`llm.py`
- 验收：`tests/acceptance/test_phase1_loss_prevention.py`、`test_task2_publication.py`、`test_task2_batch_recovery.py`、`test_publication_contract.py`

本次只读审计。聚焦原始方案的 S4 提炼合并、S5 写回、S6 溯源，以及它们对读者质量的实际影响。

## 总结

S5 的文件安全和 S6 的机器可追溯性基本落地；S4 的“防丢失”落地很多，但“知识提炼、合并、按业务结构重组”没有完整落地。当前验收主要证明“每条原文仍在、路径安全、页面不超过 300 行”，没有证明“人能读懂、主题边界合理、摘要有用、为什么/版本信息真实”。

因此，当前结果会出现：

- Markdown 原文逐行堆在 Evidence 中，内容没有真正重组；
- 页面能通过 claim/coverage/faithfulness 门，但读者看到的是低质量的摘要壳和原始行；
- S6 证明“从哪里来”，却不能证明“整理后是否更容易理解”；
- 某些失败在正式页面写入之后才被发现，fail-closed 边界顺序不正确。

#### S4 的关键缺口

1. 原始方案写的是“提炼合并”，实现的强合同是“逐行 Claim 必须保留”。后者是必要条件，不是前者的替代品。
2. Prompt 明确要求 Claim 原文逐字出现在正文（`llm.py:79-96`），在 summary 模式又把完整原文放进 Evidence（`draft.py:622`、`780-786`）。这实际上把模型限制成“生成一层摘要壳”，没有给它一个可读的知识文档生成任务。
3. 页面级合并没有使用已有目标正文：`old_target_body` 在 pipeline 中从未填充。历史内容虽在 `page_layout.py` 后续通过 claim-history 拼回，但这不是 S4 的“理解后重写”，只是确定性内容拼接。
4. 没有“主题内的语义分组”中间模型：没有概念、场景、流程、限制、FAQ、版本等 section records；`_component_spans()` 只按 Markdown 外观切块。因此输入是什么结构，输出大多就是什么结构。

## 测试覆盖的真实边界

本次聚焦测试实际为 `81 passed`。它们很强地覆盖：

- source snapshot、Claim fingerprint、line locator replay；
- 归档内容、写前归档、atomic write、路径安全；
- 300 行上限、Claim 唯一 target、Home/index/source-index 链路；
- provider malformed、taxonomy、batch resume。

但没有覆盖以下读者合同：

- 主题页是否按语义主题而不是输入批次聚合；
- 标题是否准确表达页面内容，而不是“来源标题/文件名”；
- Summary 是否比 Evidence 更容易理解，而不是逐条复述；
- Why、Version 是否来自真实 Claim，缺失时是否应该不显示空占位；
- 一个主题页是否有场景、流程、限制、FAQ、配置等可导航 section；
- 与 CompanyBrain 的读者路径、检索任务、阅读时间对比；
- source-index、Home、分类页是否能帮助读者找到“该知识什么时候用”。

例如 `test_phase1_loss_prevention.py:307-337` 只验证长文档内容全部存在和 locator 映射；`test_task2_publication.py:421-479` 主要验证 navigation records、链接和 related topic；`test_task2_corpus_regression.py:71-168` 验证固定语料、Claim/URI/fingerprint 和报告字段。这些测试可以在内容极差时全部通过。

## 结论与修复方向

### 结论

原始方案的 S5/S6 工程安全大体兑现，S4 的防丢失门兑现；但原始方案把“知识质量”写成了 Claim retention、faithfulness、max_doc_lines 等可计算门，没有把 CompanyBrain 已具备的读者模型写成可验收的输出合同。Task2 又主要增加了标题、分类、slug、导航和摘要字段，没有补齐“主题内语义重组”这一核心能力。

### 修复优先级

1. 先建立独立的“发布中间模型”：`Topic → Sections → Facts/Procedures/FAQ/Constraints/History`。页不是把 Claim 行拼起来，而是从该模型渲染。
2. 让 S4 负责主题级生成：先完整聚合，再一次性生成 section plan 和摘要；批次只作为 provider transport，不得成为知识主题边界。
3. Evidence 保留完整原文和 Claim，但正文需有“用途/摘要/关键概念/操作步骤/限制/版本/FAQ”等读者 section；缺失字段应省略，不输出“来源未说明”噪声。
4. 把“读者质量验收”加入 acceptance：固定 CompanyBrain 任务集，比较导航深度、标题可理解度、主题纯度、摘要覆盖、重复率、孤立页、人工阅读评分；Claim/Provenance 门继续保留。
5. 将 S6 校验移到 writeback 前；source-index 与 Home/分类/主题必须由同一批 records 生成，不能在写回后再直接覆盖。
6. 将 `remove_with_reason` 变成真实数据模型；没有可靠理由时只标记 `needs_review`，不能把“未理解”伪装成已归档。
