### 2. 固定字段结构（YAML frontmatter）——确认存在"13字段式"分级
以 `PAXSTORE内嵌GoInsight大屏.md` 和 `全局筛选与筛选卡片.md` 为例，两篇都用完全一致的 13 个字段：

```yaml
title: <标题>
type: concept
page_model: derived        # 或 source（原始清洗页用这个）
scope: company
product: GoInsight
section: 模块手册
module: <模块名>
tier: 2                    # 分级字段，2表示模块手册层级
trust: medium              # 信任度字段
source_status: compiled    # 表示已从源文档编译，不是原文
quality_status: formal     # 表示已进入正式层，区别于"候选页/待复核"
created: "日期"
updated: "日期"
generated_by: <脚本名.py>   # 记录是哪个脚本生成/改写的
tags: [company, GoInsight, 模块手册, <模块名>]
```

这确认了字段结构是流水线化、脚本驱动的（`generated_by` 直接写脚本名），不是人工写作。`tier`/`trust`/`source_status`/`quality_status` 四个字段构成一套内部分级/质量标签体系。

### 3. 正文栏位（非frontmatter，Markdown H2 标题）
以 `全局筛选与筛选卡片.md` 为例，实际用到的栏位：
- `## 什么时候先查这页`（相当于"适用场景/触发条件"）
- `## 筛选卡片的基本规则`
- `## 关联工作表和字段类型`
- `## 时间全局筛选的特殊边界`
- `## 和工作表筛选的叠加`
- `## 与维度格式化的关系`
- `## 排查路径`（相当于"常见问题/FAQ"，但是以决策树形式呈现，不是问答对）
- `## 和其他页面的关系`（关联模块，用 `[[wiki链接]]` 语法）
- `## 来源索引`（列出被综合的多篇源URL+更新时间）

`PAXSTORE内嵌GoInsight大屏.md` 用的是另一套栏位：`## 场景定位`、`## 嵌入展示机制`、`## 首页默认大屏`、`## 详情页默认大屏`、`## 应用详情页默认大屏`、`## 常见误解`、`## 推荐入口`。

**结论：栏位不是严格统一的13个固定字段模板，而是 frontmatter 层统一（13个key固定），正文层按页面语义自由命名 H2 标题**（用户反馈中提到的"13字段分级"更准确的说法是"13个 YAML 元字段固定+正文标题自由"）。

### 4. 知识图谱式组织
存在，但只是轻量的 wiki 双向链接，不是真正的图数据库/图谱：
```
## 和其他页面的关系
- 时间范围和时间间隔见 [[时间筛选与查询性能边界]]。
- 普通文本和批量输入筛选见 [[文本、数值与位置筛选]]。
- 图表联动见 [[关联筛选与图表联动]]。
- 维度格式化影响见 [[字段格式化、配色与条件样式]]。
```
以及跨模块引用（相对路径）：
```
- 默认大屏配置：[[../大屏/默认大屏与智能大屏]]
- Child Reseller 口径：[[../组织与权限/Child Reseller查询身份与业务口径]]
```
这是纯文本 Markdown wiki-link，没有节点属性、边类型、权重等图谱要素，本质是"看到某问题去查哪篇"的导航列表。

## 三、关键脚本逻辑（信息丢弃证据）

## 五、结论：反馈是否成立

用户反馈"结果太简略、遗漏太多知识"——**证据支持这个反馈，且丢失是系统性、脚本硬编码的，不是个别失误**：

1. **硬限流丢弃**：`max_lines=12`、`limit=8`、`limit=3`、`limit=6`、`scored[:3]` 等多处硬编码上限，源文档信息量再大也只能进入极少条目。
2. **规则性丢弃特定类别**：问号结尾的行（FAQ原始问句）、纯字母数字行（参数/错误码/URL）、双语文本中的英文部分、Source URL/Page ID/Version等溯源元数据，均被规则命中即删除，不是"总结不到"而是"设计为不保留"。
3. **决策动机(why)系统性丢失**：脚本的"关键细节"区块只挑"可校验事实"（第339行原文用语），不挑"需求背景/原因"类段落，导致所有"为什么这么设计"的内容在提炼链条里没有落脚点。
4. **版本历史丢失**：产出页 frontmatter 只留 `created/updated`，源文档里的版本号、修订记录表格没有对应字段承载。
5. **视觉设计稿引用丢失**：蓝湖链接、截图引用在提炼脚本里没有任何处理逻辑（脚本正则只处理文本行），必然全部丢失。
6. **来源可信度虚标**：抓取失败的空壳源文档仍可能被列入"来源索引"，造成表面上"有据可查"、实际上无信息增量的假象。

**唯一需要澄清、不构成丢失证据的点**：`prune_low_value_formal_sources.py` 与本次反馈无关，它只删6个年假计划文档，不要把它算作"丢弃GoInsight知识"的证据。

**建议方向**（仅陈述事实观察，不代表已实施的修复方案）：如果要改善"遗漏太多"的反馈，直接可改的参数是 `enrich_goinsight_module_guides_from_source.py` 里的 `max_lines`/`scored[:3]` 硬编码上限，以及 `clean_product_source_docs.py` 里 `pick_facts/pick_summary/pick_basis` 的 limit 参数；更根本的结构性缺口是"决策动机(why)"和"版本历史"目前在13字段体系里没有对应字段承载，需要新增字段而非只调参数。
