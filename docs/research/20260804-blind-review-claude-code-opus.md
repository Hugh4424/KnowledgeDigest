## 结论

1. Task2 难读的根因只有两条：**主题边界由传输批次和来源文件决定**（batch_size=1 + `cluster()` 只在批内比较，85/86 单来源主题），**正文由"逐字保真"合同锁死**（publication-only 禁止 `final_body`、`llm_summary_enabled: false`、要求 claim 原文逐字出现在正文）。哈希文件名、空分类、Related topics 全空、300 行分页都是这两条的下游症状。
2. 第三条被低估的根因是**降级一律 fail-open**：embedding 探测失败整次回退词面 Jaccard 后照常正式发布；单来源簇因 `pair_scores` 为空、`min_pair=1.0` 自动进最高置信；30 次 provider 失败仍生成正式页；89/89 批 `succeeded` 而 `quality.status` 全空。质量在每个失败点都向"仍然发布"倾斜。
3. 原方案的保存层基本兑现（S1 指纹/空壳门、S5 原子写与写前归档、S6 claim 级回溯）；**知识发布质量从未进入原方案的合同**——S3 的 LLM 路径判定、S4 的"提炼合并"、F1–F7 多特征决策、`remove_with_reason` 三分类都没有落地，`old_target_body` 从未填充，所以 revise/merge_multiple 在语义上是空的。
4. 修复方向报告的诊断准确，但**修复设计重复了造成故障的那一处耦合**：它仍要求"每段必须绑定 Claim/Evidence"。若沿用现有的逐字包含式忠实性校验，Evidence-as-body 会原样复发。无损与可读必须落在两个不同产物上。
5. 修复方向存在明确过度设计：v1 就要 8 种页面类型、10 字段 `KnowledgeEntity`、raw/candidate/formal 三态 + 5 类 needs_review 原因。89 篇语料撑不起 8 种类型，结果会重演"13/21 空分类"；而原方案的非目标里本来就写着"不设计人工复核流程"，三态治理是范围扩张，报告未承认这一点。
6. 优先级错误：报告把本体建模放任务 A、读者质量门放任务 C。实际最便宜、最高杠杆的三件事（失败/降级不进正式导航、账本闭合与 S6 前置、主题跨来源聚合）都不需要完整本体，而且能立刻把 58 个占位页从正式导航移除。
7. 重大遗漏：**增量语义**。原方案核心场景是 `digest(new_dir, kb_dir)`；报告的"全量快照 → 全量 TopicPlan → 全量编译"把它变成了一次性全量编译器，却未回答下一批 10 篇来源如何并入、已发布正式页是否重编译、人工修订是否被 `managed_by` 整文件覆盖。
8. "来源按主题编译成产品/模块/场景/规则/技术/经验页面"应作为核心的**只有前半段**：跨来源主题聚合 + 正文编译是核心；页面分型是手段，v1 压到 3 型，且类型和模块目录必须**数据驱动出现**（有 ≥N 个真实实例才允许存在），这正是 CompanyBrain 模块总览"模块目录按真实资料自动出现"的做法。

## 根因证据

**主题粒度（机械因果，不是模型问题）**
- `batch-state.json`：`batch_size: 1`、89 批、89 个唯一 `source_paths`、全部 `succeeded`。
- `cluster()` 签名只有 `raw_items` + 一个 scorer，不含 `kb_dir` 已有条目索引；页面预取发生在 S3 之前，不参与 S2。
- 结果：86 簇 = 85 单来源 + 1 双来源，全部 `auto`；`topic_id` 是来源 ID 集合的哈希。
- 推论：单改批大小只能在批内合并，跨批仍分裂。必须把主题规划的输入改成全量来源 + 已有 KB 主题索引，这是两个独立缺陷叠加，报告只指出了"批次不应是知识边界"这一半。

**正文即证据（合同冲突，不是提示词问题）**
- `publication_only` 提示禁止返回 `final_body`；运行记录 `llm_summary_enabled: false`。
- summary 模式把 `final_body` 强制设为完整 `evidence_body`；提示要求 claim 原文逐字出现在正文；`default_generator` 是原文身份回写。
- `old_target_body` 在 pipeline 中从未填充，所以 `revise` 传入的已有正文为空。
- 样本证实：`task2-page-dashboard` 的 Evidence 从"# 1.背景介绍"到"文档更新历史"表格再到 3.1.6 折线图刻度规则，是 Confluence 导出的原始顺序；`task2-page-ae` 的 Summary 是占位语，Version 是 `Missing`，正文是带 8 张 thumbnail URL 的操作碎片。
- 结论：忠实性被实现为"逐字包含"，这在数学上排除了重组。所谓"S4 未实现"其实是"S4 被现有硬门禁止实现"。

**降级 fail-open**
- jina 探测失败 → 整次运行回退 Jaccard → 仍产出正式发布物。
- iOS 日志来源以 Jaccard `0.645161` 选中 iOS capability 页，其余候选约 `0.08`：这是词面阈值路由，不是语义判断。
- 单来源簇 `pair_scores` 为空、`min_pair=1.0`，只要 token ≥3 即 `auto`：**"无证据"被当成"最高置信"**。
- 30/31 provider 失败（9 deadline、22 非 JSON）→ 58/120 页 Summary 占位、58 页 Why 占位、54 页 Version 缺失、fallback ratio `0.471591`；这些页仍在正式导航内。

**账本本身不可作为验收依据**
- source-index 88 行 vs batch/snapshot 89 个来源；缺口来源快照明确 `source has no body`，既未发布也未标记。
- claim-history 失败行 4,904 vs pending-review 4,756；18,724 行仅 18,277 唯一 `claim_id`；snapshots 178 行/89 唯一；`duplicates.jsonl` 同一关系写两遍（非幂等）。
- S6 `audit_provenance()` 在 writeback **之后**调用；`_write_source_index()` 在事务之外单独覆盖。fail-closed 顺序倒置。
- 90 份报告 `official_write=written`，全体 `quality.status` 空、`benefit_status=unmeasured`；`COMPARISON.json` 把 17 条 `agent_assisted_pass` 记成 `title_understood`，而 tasks 台账里 AC-007 人工确认仍开放。

**CompanyBrain 更好的可复核差异**
- 主轴是产品（Products 750/838），Task2 主轴是领域（客户/研发/运营/其他/原则/产品）；`product_slug` 非空为 0。
- 入口页带决策信息：Home 写"企业正式知识库/查询建议/使用边界"，产品索引给"优先入口/按能力查/产品清单/使用边界"，模块总览给每模块页数。
- 正式层 0 个 hash 或 `ae`/`ios`/`global` 式文件名；412 页有 `page_model`+`quality_status`，260 页有使用边界，603 页显式记录来源。
- 治理承认不确定：GoInsight 保留 60 个 `uncertain_module`、13 个对象目录错位告警，低置信进"资料汇总"（60 页）而不是伪装正式页。
- 注意反例：CompanyBrain 路径深 5 跳仍更好用。**"跳数 ≤4"是错的指标**，它会惩罚更好的系统。

## 原方案实现缺口

已实现（保存/溯源）：S1 读取/URI/指纹/空壳门/快照；S2 complete-linkage 形态与三层队列；S3 top-k 候选；S5 临时文件+fsync+原子 rename+写前归档+路径安全；S6 claim→source_uri/定位/指纹/验证状态与归档不删除；Task2 的受控 taxonomy、稳定 topic ID、Home/indexes/pages、300 行分页、source-index。

只实现了形式、没有实现知识质量：
- 九条防丢失里三条只有保留没有可用性：`max_doc_lines` 变成 300 行硬切（且忽略传入 `max_lines`），不规定一页回答什么；非文本引用只是正则 URL 列表，图片/附件/父子页无一等模型；表格原样留在 Evidence，未语义化。
- why/版本"强制字段"通过字段存在性校验，实际由固定占位语满足——**字段合同被占位语合法绕过**，这是原方案可被形式满足的设计漏洞。

完全未实现：
- S3 的 LLM 路径判定（正式主路径是 `len(selected)` 规则，不是回退）。
- F1–F7 多特征决策（只有一个相似度分数；换 embedding 只是换分数来源）。
- S2 输入的"已有 KB embedding 索引增量维护"。
- S4 的"提炼合并"与 `keep/revise/remove_with_reason` 真实协议（`removed_claims` 只来自 `unsupported:` 前缀）。
- 归档语义不统一：正式路径拒绝 `obsolete_target_paths`，旧 `remove_only` 分支仍 `unlink()`。
- 产品/模块/对象/任务/边界/关系模型，及总览页、模块页、场景索引、边界页的页面职责合同。
- 面向真实问题的读者验收。

## 对当前修复方向的批评

**必须纠正的设计错误**

1. **"每段必须绑定 Claim/Evidence"会复发 Evidence-as-body。** 现有忠实性门是逐字包含 + claim 全覆盖，正是它把 Summary 逼成逐条复述、把正文逼成原文。必须显式改成：正文段落引用 claim **id**（不含原文），忠实性由抽样蕴含检查 + 无损由独立档案产物保证。修复方向没有触碰这个机制，风险最高。
2. **"跳数 ≤4"与"人工理解度 ≥90%"作为硬门是错的。** 前者惩罚 CompanyBrain 式深层导航；应改为"每一跳都提供决策信息（适用问题/边界/下一跳）"+"首次命中正确率"。后者在 17–20 个样本上错 2 个就失败，统计上不稳，且已被 `agent_assisted` 冒充过一次；必须预注册抽样种子、样本量、评审人和原始评分表，否则这个门会被自我认证绕过。
3. **主轴未拍板。** 报告同时保留领域 taxonomy 和产品/模块本体，却没说目录主轴是哪一个。必须定：**主轴=产品/系统，领域降为 facet 索引**。否则 51 页混装 `product-capability` 的问题会在新目录里换个名字重现。
4. **产品字典的写入权未定义。** 若允许 LLM 自动扩展本体，会产生别名爆炸和产品幻觉。字典必须是受管、可人工编辑、纳入版本控制的文件（CompanyBrain `module_rules.json` 模式），模型只能提议 + 标注低置信。

**过度设计**

- v1 八种页面类型 → 压到 3 种：①对象/功能页（用途·入口·前置·步骤·规则·异常·限制·版本·来源）②产品/模块总览页（生成式导航，带页数与适用问题）③原文档案页（raw，承接失败与未编译来源）。经验页、版本页、案例页等待语料里出现足够实例再开，且类型必须数据驱动出现。
- 10 字段 `KnowledgeEntity` → v1 只需 `产品 slug + 别名`、`模块 slug（产品内）`、`对象名`、`置信度`。角色/场景/边界先作为页面字段，不建独立实体。
- raw/candidate/formal 三态 + 5 类 needs_review → v1 两态：**可发布** / **不可发布（含原因码）**。原方案明确不做人工复核流程；三态 + 无人审 = candidate 永久堆积（CompanyBrain 60 个 uncertain_module 就是这个结局的写实版）。若确要三态，必须同时给出评审人、节奏、抽样比例和晋级判据，否则这是纸面治理。

**遗漏**

- 增量与重编译语义（第 7 条结论）：全量 TopicPlan 与 `digest(new_dir, kb_dir)` 的关系、稳定 ID 跨运行不变性、已发布页的重编译策略、人工修订在 `managed_by` 整文件托管下如何不被覆盖、旧路径→新路径重定向映射。
- 降级治理没有成为一等要求：embedding 整次回退、单来源簇自动 auto、provider 失败仍发布，三者是同一个 fail-open 缺陷，报告只批评了第三个的表现。
- S6 前置与 source-index 进事务未列入任务，但这是低成本、可测试、直接影响"能不能相信验收数字"的修复。
- 账本闭合（88/89、4,904/4,756、duplicates 非幂等、快照重复行）未列为发布硬门。若账本不闭合，任何"machine gates 全绿"的声明都不可信。
- 20 个读者问题的**选取方法**未定义（谁出题、覆盖哪些产品/角色、是否含"应当查不到"的负样本）。

**优先级错误**

任务 A 产出的是纯规格文档且不跑真实 provider。Task2 已经证明"规格里字段齐全"不能保证质量。规格必须以 12–20 篇语料的真实端到端产物作为验收物，而不是以文档自证。因此任务 A 应大幅压缩并与任务 B 合并；读者质量门从第一天起每次运行都跑，不是留到任务 C 验收。

## 建议的最小可行修复架构

保留原方案"不引入框架"的定案，不引图数据库、不引向量库、不引调度器。保留 S1/S5/S6 全部机器安全门。改动集中在四处。

**A. 保存层（不动，只补三个修复）**
- S6 审计移到 writeback **之前**，失败即阻断，不产出正式页。
- source-index、Home、分类页、主题页由同一批 records 一次写回，取消事务外覆盖。
- 账本幂等化：`(source_uri, content_fingerprint, fragment_locator)` 为稳定身份；duplicates 一关系一行；快照不写重复行。

**B. 主题层（TopicIndex，替代"cluster 即主题"）**
- 输入：**全量来源 + 已有 KB 主题索引**（不是批内 raw_items）。
- `topic_id = f(产品 slug, 对象名规范化)`，与来源 ID 集合、批次、运行顺序无关。
- 产品/模块 slug 来自受管字典（种子：语料里实际出现的产品，约 24 个），模型只提议。
- 无法确定产品或对象的来源 → 不可发布，进原文档案页 + review 队列。
- 单来源可以成主题，但必须先归属产品/对象；同产品同对象存在其他来源时必须合页。

**C. 编译层（PageDraft，3 种类型）**
- 输入：主题全部成员来源正文 + 已有目标页正文（必须真正填充 `old_target_body`）。
- 输出：正文段落 + 每段的 claim id 引用；**正文不含逐字原文块**。
- 忠实性：claim id 可解析 + 抽样蕴含检查；无损由档案页/`_digest` 保证，不再由正文承担。
- 证据分离：正文页只留"来源"链接区；原文进 `sources/` 档案页或 `_digest`。

**D. 发布层**
- 导航：Home（带查询建议与使用边界）→ 产品索引 → 产品总览 → 模块总览 → 页。空分类/空模块**不生成**。
- 相关主题只能来自结构性证据（同产品同模块、共享来源、原文显式互引），双向且可验证；无关系就明确写"无"，禁止模型自由生成。
- 交付分两包：知识包（README/Home/indexes/pages/sources/source-index）与审计包（`_digest`/`_archive`/provider 日志/对比报告）。
- 一次运行只有两个终态：**published** 或 **degraded（不写 formal 目录）**。

## 任务拆分与顺序

**任务 0：诚实化（不改架构，1 步到位，最高性价比）**
- S6 前置、单事务写回、账本闭合门、`degraded` 运行不得写 formal。
- provider 失败 / embedding 降级 / 无产品归属的来源移出正式导航，改为原文档案页 + Home 上可见且带计数的待复核入口。
- 冻结当前产物为只读基线；同时定下 20 个读者问题、抽样种子、评分表和评审人。
- 立即可观测的效果：58 个占位页离开正式导航，剩余约 62 页是真实内容；同时"machine gates 全绿"第一次变得可信。

**任务 1：主题粒度**
- 产品/模块受管字典 + TopicIndex（全量输入）。
- 批次边界不变性回归：同一语料按 1 篇/批 与 20 篇/批 各跑一次，topic 集合与页面路径必须逐字节一致。
- 路径规则改造 + 旧路径→新路径映射表。

**任务 2：正文编译（12–20 篇代表性语料）**
- 解除逐字包含合同，改 claim-id 引用 + 抽样蕴含；填充 `old_target_body`；`remove_with_reason` 成为真实数据协议（无可靠理由时只标 needs_review，不得伪装归档）。
- 3 种页面类型 + 正文/证据分离。
- 每次运行都跑 20 问读者门（此时只在小语料上跑）。

**任务 3：导航与全量发布**
- 产品索引/产品总览/模块总览（数据驱动出现）、空页不生成、相关主题结构性生成。
- 冻结字典/模型/预算/输入 manifest 后全量运行；交付包分离。
- 同一套 20 问对比 Task1 / Task2 / CompanyBrain / 新结果，人工评审留原始记录。

顺序理由：任务 0 先做，因为它不依赖任何新架构却移除了一半可见垃圾并修复了验收可信度；任务 1 先于任务 2，因为把错粒度的主题编译得再好仍是错页面；导航放最后，因为导航是主题层与编译层的函数，提前做会返工。

## 硬质量门禁

机器门（全部可自动化，任一失败即 degraded，不写 formal）：

| 门 | 判据 |
|---|---|
| 批次不变性 | 批大小 1 与 20 两次运行的 topic 集合、页面路径逐字节相同 |
| 主题粒度 | 单来源主题占正式主题 ≤60%（当前 98.8%）；同产品同对象来源不得分散在多页 |
| 产品归属 | 正式页 `product_slug` 非空率 100%（当前 0）；无归属只能进档案页 |
| 路径可读 | 正式页路径禁含 ≥8 位 hex；禁 `1.md`/`ae.md`/`ios.md` 式名；路径必须含产品 slug |
| 正文非证据 | 正文页逐字来源行占比 ≤20%；正文 ≤120 行；正文区不含原始图片 URL 堆 |
| 零占位 | 正式页占位语（"来源未提供摘要"/"来源未说明"/`missing`/"暂无已验证的相关主题"）出现次数 = 0；缺失字段省略 |
| 降级 fail-closed | embedding 探测失败 = 硬失败；provider 失败主题不产正式页；单来源簇不得因 `pair_scores` 为空自动 auto |
| 账本闭合 | batch sources = snapshots 唯一数 = source-index 行数；失败 claim 集合 = pending 集合；duplicates 幂等；S6 在写回前通过 |
| 导航完整 | 无空索引页；待复核入口非空且计数与队列一致；source-index 目标为可点击链接；分页页有主题总览与上下页 |
| 关系可验 | 每条相关主题可追到结构性依据且双向存在 |
| 交付分包 | 知识包不含 `_digest`/`_archive`；知识包体积与正文量同量级 |
| 状态不互冒 | `machine_pass`/`agent_assisted`/`human_reviewed` 三字段独立；`written` 不得覆盖 `quality` 空值 |

读者门（人工，预注册）：
- 20 问（含 2–3 个"应当查不到"的负样本）全部有入口，**首次命中正确率 ≥85%**；不设跳数上限，改为"每一跳都有适用问题/边界/下一跳说明"。
- 正式页标题脱离路径仍能说明对象与用途：人工理解 ≥90%，样本量与抽样种子事先固定。
- 产品/模块归属人工准确率 ≥90%，不确定项进 review。
- 正文能回答"是什么/怎么用/限制/异常/适用版本/来源"，不需打开档案页。
- 任一维度不通过 → 整体只能叫 candidate，禁止称"发布完成"。

## 最危险的三条误区

1. **"先把本体和 8 种页面类型的规格写完，质量就会跟着来。"** Task2 已经反证：受控 taxonomy、语义标题、字段回指、300 行分页、316 项测试全部就位，产物仍是原文切片器。规格能被占位语和形式校验合法满足。任何新规格的验收物必须是 12–20 篇真实语料上的端到端产物，而不是规格文档自身。

2. **"只要每段都绑定 Claim/Evidence 就既无损又可读。"** 这正是现故障的成因：逐字包含 + claim 全覆盖在数学上排除了重组，把 Summary 逼成复述、把正文逼成 Evidence。无损与可读必须落在两个产物上（档案页保原文、正文页保可读），忠实性用 claim id 引用 + 抽样蕴含检查，不能靠字符串包含。沿用旧机制的"新架构"会精确复发同一结果。

3. **"人工验收会兜住质量。"** 现状是 `agent_assisted` 被记成 `title_understood` 通过、AC-007 长期开放、`quality.status` 全空而 `official_write=written` 被下游读成完成、89/89 `succeeded` 掩盖 30 次 provider 失败。人工门只有在有技术阻断时才存在：未审、降级、账本不闭合的运行**在代码层面不允许写入 formal 目录**。否则它只会成为又一个永久开放的待办，而 candidate 区会像 CompanyBrain 的 60 个 uncertain_module 一样无限增长。
