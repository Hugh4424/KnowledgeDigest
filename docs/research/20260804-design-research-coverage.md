# 原始方案与调研覆盖度审查

日期：2026-08-04  
范围：`docs/plans/universal-knowledge-digest-design.md`、`docs/research/`、Task2 规格 `specs/archive/knowledge-digest-llm-naming-classification/spec.md`。本报告只审查“方案是否考虑了知识质量、调研是否支撑方案”，不判断 Task2 代码实现细节。

## 结论

原始方案对“工程安全”和“信息不丢失”考虑较完整，对“知识是否值得读、是否能帮助人完成任务”考虑不足。它把“Claim 可追溯、Evidence 存在、页面不超长”当成了知识质量的主要代理指标，因此允许系统产出“没有丢原文、但读者无法使用”的页面。

Task2 规格后来补上了 taxonomy、Home、语义标题、LLM JSON 合同和 CompanyBrain 阅读抽样（`spec.md:30-69`、`spec.md:73-130`、`spec.md:142-172`），方向是对的；但它仍把发布层建模成“主题页固定字段 + Evidence”，没有把 CompanyBrain 的核心能力——知识本体、页面职责、场景入口、正文编译、低置信治理——变成一等设计对象。当前低质量结果不是单一模型故障，而是方案层质量合同不够完整造成的。

## 一、已覆盖的内容

### 1. 原始方案覆盖了安全底线

- S1–S6 的基本流水线、空壳来源门禁、聚类、提炼、写回和溯源都有定义（原始方案 `:81-119`）。
- 9 条“防信息丢失”对策明确覆盖：不截断、保留 FAQ/双语/错误码、why/版本字段、非文本引用、坏来源隔离、归档不删除、保留表格结构（原始方案 `:172-184`）。
- 写前归档、原子写、Claim 级来源和 `removed_claims` 快照等机制，能防止静默丢资料（原始方案 `:107-119`）。
- 调研本身能识别 CompanyBrain 的真实丢失模式：原始 `sc-cb-analysis.md:137-154` 明确记录截图丢失、结构扁平化、时效丢失和截取式摘录的后果。

这些内容解释了为什么 Task1/Task2 仍然能通过“Claim、Provenance、hash、归档、行数”类检查；但它们只能证明保存和回溯，不等于知识被编译成可读产品。

### 2. 调研覆盖了算法来源和工程取舍

原始方案引用了 ovmc 聚类、sleep-curator 生成、CompanyBrain 丢失分析和开源项目对比（原始方案 `:8-24`）。现有 `docs/research/` 也包含对应文件，并额外有 CompanyBrain 内容、IA 和阅读路径分析。

这些调研足以支撑：

- complete-linkage、top-k、claim verify、faithfulness 等机制选择；
- 不引入数据库、图框架、调度器和重量事务；
- 归档而不是删除；
- 使用文件 KB、可离线运行、provider 可替换。

### 3. Task2 已识别部分发布层问题

Task2 规格明确提出：不能把 Claim 数量当成功标准，必须有 Home、语义标题、用途、Summary、Why、Version、Related topics 和来源索引（`spec.md:8-12`、`:30-43`）。它也增加了受控 taxonomy（`:45-61`）、读者导航（`:63-69`）、语义 JSON 合同和字段回指（`:73-123`），以及 CompanyBrain 20 主题阅读对比（`:166-172`）。

这是正确方向，但规格中的“字段存在”仍比“字段有用”更明确；实现很容易通过形式校验后留下占位文本。

## 二、部分覆盖或设计不足

### 1. “防丢失”覆盖了保留性，没有覆盖知识价值

原始方案的目标是“杜绝信息丢失”（`:50-54`），S4 主要要求 claim-level verify 和 faithfulness（`:102-109`）。这回答了“生成内容是否能回指来源”，没有回答：

- 读者要解决的具体问题是什么；
- 页面是否只负责一个稳定对象/任务；
- 信息是否按业务顺序重组；
- 是否有适用范围、限制、异常、排查和反例；
- 页面之间的关系是否能引导下一步；
- 低置信度内容是否应该暂不进入正式知识库。

因此“原文全部在 Evidence 中”可能被验收为无损，即使正文只是原文堆叠或模板占位。

### 2. 缺少知识本体与页面规划阶段

原始管线直接从 `Cluster` 进入 `EvolutionDecision` 和 `Draft`（`:95-109`），没有独立的：

`来源类型 → 产品/模块/业务对象 → 知识类型 → 页面规划 → 场景入口 → 正文编译`

CompanyBrain 调研已经提供反例：`sc-cb-analysis.md:96-133` 记录了产品、模块、场景索引、边界页和“资料汇总→正式页”的两阶段编译；`20260804-companybrain-content.md:51-59` 也明确指出需要先建模再编译。原始方案没有把这些内容提升为 S0 或 S4 前的正式阶段，导致分类只能贴标签，不能形成语义结构。

### 3. 分类设计只有分类表，没有分类证据和对象字典

原始方案只要求 KB 结构约定声明字段/目录（`:147-150`），没有规定如何从 Confluence 内容识别产品、模块、对象、任务和边界，也没有规定词典、别名、冲突和低置信处理。

Task2 的固定两级 taxonomy（`spec.md:47-59`）比原始方案好，但 `product-capability`、`implementation` 等叶分类仍是通用标签。没有产品/模块字典和关系模型，系统即使分类合法，也可能把多个产品、模块和任务混在同一主题页。

### 4. 拆分被定义为安全阀，不是阅读设计

原始方案把 `max_doc_lines` 定义为“超过阈值就建议拆分”，并强调重组而非丢弃（`:176`、`:199-201`）。没有定义：一页回答什么问题、如何按对象/任务切页、分页之间如何连贯、哪个页面是总览、何时建立场景索引。

Task2 虽然固定了 300 行和导航合同（`spec.md:63-69`、`:142-152`），仍主要是页面数量、行数和链接门禁。300 行只能防巨页，不能把一篇混合部署/迁移/权限/数据库检查的来源变成可读知识。

### 5. 缺少“正式页/资料汇总/待审”生命周期

原始方案明确把 needs-review 设计成“只产出队列文件，不设计人工复核流程”（`:56-62`、`:87-93`）。这在工程简化上合理，却直接缺少 CompanyBrain 的核心治理：低置信内容先放资料汇总，经过编译和审核后才进入正式页。

Task2 用 `pending` 和 `needs-review` 补了一部分（`spec.md:57-61`、`:128-130`），但没有定义从 pending 到 formal 的编译/晋级规则、质量报告、人工修订如何回流模型或稳定索引。因此不确定内容仍可能以“合法但无用”的正式页发布。

### 6. 缺少读者质量的硬验收

原始方案的 Phase 0/1 验收是构造 fixture、空壳页、高密度页、超长文档和溯源（`:190-202`）；Phase 3 只验证 3 个新输入、隔离 KB 和 provenance（`:215-219`）。没有固定真实语料的阅读任务、标题理解、导航耗时、答案完整性或人工对照。

Task2 才首次加入 `title_understood`、`summary_faithful`、`usage_boundary_visible` 和 `reader_time_seconds`（`spec.md:166-168`），但这是后补的发布验收，不是原始方案的质量基础；从当前结果看，执行时也没有把这些指标作为“未通过即停止”的发布门。

### 7. 没有明确区分“缺失事实”和“生成失败”

原始方案允许字段由 KB 约定承载，但没有定义缺失语义。Task2 规定没有 why/version 时写固定缺失文本（`spec.md:34-43`），这能防臆造，却会把大量页面变成模板壳：形式上完整，读者仍不知道页面用途、适用边界和更新时间。正确设计应区分：

- 来源确实没有该事实；
- 模型没有生成；
- 来源冲突，不能判定；
- 需要人工编译后才能发布。

四者不能共用一个占位字符串。

## 三、调研文件还缺什么

### 已有调研的优点

- `ovmc-analysis.md`、`sleep-curator-report.md`：算法和依赖链证据充分。
- `goinsight-loss-report.md`、`sc-cb-analysis.md`：能指出 CompanyBrain 清洗阶段的具体信息损失，也能看到正式编译页与资料汇总页的差别。
- `20260804-companybrain-content.md`、`20260804-companybrain-reader-journey.md`：已经开始记录 Task2 的页面统计、入口、占位字段、文件名和读者路径。

### 对原始方案而言仍缺少的调研

1. **完整 CompanyBrain 编译协议**：哪些页面类型由哪些脚本/人工规则生成，页面晋级条件是什么，哪些字段是输入元数据、哪些是编译结果。现有调研有样例和结论，但没有把协议抽成可执行规范。
2. **知识单元与粒度研究**：一个页面对应产品、模块、对象、任务、规则、版本还是问题；同一来源如何拆成多个页面；何时合并/何时分开。没有这一层，聚类结果天然会被误当作页面规划。
3. **真实读者任务研究**：员工查产品能力、研发排障、运营判断、客户答疑分别从哪里开始、需要哪些字段、可接受多少跳。现有阅读报告记录路径，却没有固定问题集和答案评分。
4. **Confluence 数据特征研究**：标题模板、父子页、表格、截图、FAQ、版本页、重复导出、跨产品引用、中文/英文混排等在 89 篇语料中的比例与处理策略。
5. **语义质量失败样本集**：巨页、重复标题、hash 文件名、空分类、占位摘要、错合并、过度拆分、缺失边界、版本冲突各自的最小复现样本和停止条件。
6. **模型质量与回退研究**：LLM 输出失败、摘要泛化、错误分类、相关主题幻觉、表格重写损失的人工标注集；不能只测 JSON 合法和 Claim 回指。
7. **长期治理研究**：人工修订如何保留、版本如何比较、旧页面如何重编译、低置信度如何晋级、用户反馈如何进入下一次发布。
8. **研究资产可复现性**：原始方案用 OpenViking 的绝对路径引用外部调研（`:8-24`），没有在方案中绑定快照 hash、版本、采样清单和生成命令；路径当前可用，但方案脱离外部 repo 后仍不具备自证性。

## 四、对当前低质量结果的直接解释

当前结果很可能同时满足了 Task1 的“保留/溯源”合同和 Task2 的部分“发布形式”合同，却没有满足用户真正要的“知识产品”合同：

1. 聚类被直接当成主题，缺少业务对象和任务规划。
2. 通用 taxonomy 被当成知识结构，缺少产品/模块/场景关系。
3. Evidence 被当成正文主体，缺少 CompanyBrain 式编译重组。
4. 300 行分页被当成可读性，缺少主题总览、连续分页和跨页关系。
5. 缺失字段被固定占位，缺少“原文缺失/模型失败/冲突/待编译”的状态区分。
6. 机器门禁检查“有没有”，没有检查“是否能回答问题”。

## 五、修复方案应如何改写设计

下一版不要继续在 `publication.py` 上堆标题和索引字段；应把架构改成“两层合同”：

```text
保存层：原始来源 → Claim/Evidence/Provenance/Archive（不丢、不伪造）
发布层：来源清单 → 知识本体 → 页面规划 → 正文编译 → 读者验收 → 正式发布
```

发布层至少需要以下独立职责：

1. **知识本体**：产品、模块、业务对象、任务、知识类型、版本、边界、置信度、别名和关系。
2. **页面规划**：决定总览页、模块页、场景页、规则页、排障页和来源页，不让 cluster 直接变 page。
3. **正文编译**：按页面类型组织“是什么/何时使用/步骤或规则/限制/异常/版本/来源”，Evidence 只做引用，不做正文替代。
4. **治理状态**：`raw → candidate → formal → needs_review`，记录质量报告和人工修订，不把低置信结果伪装成完成。
5. **读者验收**：固定真实问题集，验收入口、标题、摘要、任务答案、边界、版本、跨页导航、来源回溯和阅读时间；任何关键维度失败都不得称为发布成功。

原始方案的 S1–S6 和 Task2 的无损/安全门应保留，但必须明确它们是“保存层底线”，不是“知识质量完成”。
