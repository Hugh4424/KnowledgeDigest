# 原始方案 S1–S3 实现审查

审查对象：

- 原始方案：`docs/plans/universal-knowledge-digest-design.md`
- 实现：`src/knowledge_digest/ingest.py`、`cluster.py`、`retrieve.py`、`pipeline.py`、`batch_run.py`
- 验收：`tests/acceptance/test_phase0_digest.py`、`test_phase4_calibration.py`、`test_task2_corpus_regression.py`
- Task2 现场：`/Users/Hugh/Downloads/KnowledgeDigest-task2-qwen-final9-20260804`

## 结论

S1 基本实现的是“把本地文件安全读进来”；S2/S3 基本实现的是“用一个相似度分数做去重/更新路由”。这足以通过现有构造型验收，但不等于已经实现了读者需要的“知识主题建模、语义分类和可读结构”。

最关键的证据来自 Task2 的固定批次计划：`company-kb/_digest/batch-state.json` 中共 86 个簇，其中 85 个是单来源簇、1 个是双来源簇，且 86 个全部被判为 `auto`。这说明 S2 主要把每篇来源当作一个独立主题，而不是把同一产品/领域下的多篇资料组织成读者可理解的知识主题。后面的 Task2 分类和页面发布只能在这个错误的主题粒度上补标题，无法弥补上游结构缺失。

原始方案 S1 只要求“统一 RawItem + 空壳门禁 + content_hash”（设计文档 `:81-85`），所以从字面看完成度较高。但方案没有规定标题/H1、来源层级、Confluence 页面层级、表格/代码/附件等结构化归一，也没有信息密度、语言、模板噪声等读者质量指标。S1 因而把大量“合法但不可读”的正文原样交给下游；这属于原始方案的质量设计缺口，不只是代码漏实现。

## S2 聚类判断（Cluster）

### 对照实现

| 设计要求 | 实现状态 | 证据与影响 |
|---|---|---|
| complete-linkage，避免弱链合并 | 部分实现 | `cluster.py:32-52` 对当前 pending 列表按种子逐个扩展，并要求新成员与已有成员的最小相似度达阈值；形态上是 complete-linkage，但不是全局凝聚式聚类，结果受 seed/排序影响。 |
| 双阈值 auto/needs_review/insufficient | 已实现 | `cluster.py:44-52` 用 `high/medium` 分层；`cluster.py:70-78` 将后两层写入队列。验收 `test_phase0_digest.py:689-710` 只验证低置信簇进入队列。 |
| 复用 F1–F7 多特征决策思路 | 未实现 | 设计文档 `:87-93` 明确要求多特征决策树并重新标定阈值；实现只调用一个 `SimilarityScorer.score`（`cluster.py:31-43`），没有标题/产品/路径/版本/实体等特征组合。Embedding 只是替换同一个分数来源，不是多特征决策。 |
| 使用既有 KB 的 embedding 索引并增量维护 | 未实现（S2 层） | 设计要求输入包含 `kb_dir` 已有条目的 embedding 索引；`cluster()` 签名只有 `raw_items` 和一个 scorer（`cluster.py:20-29`），只在新来源之间比较。`pipeline.py:99-129` 的页面预取发生在 S3 前，供页面检索，不会参与 S2 聚类。 |
| 输出 Cluster 与待复核队列 | 已实现 | `cluster.py:57-68` 输出 `cluster_id/topic_id/members/tier/source_uris`；`cluster.py:70-78` 写队列。 |

Task2 的真实计划进一步证明 S2 没有建立读者主题层：

```text
batch-state.json -> cluster_plan: 86 个簇
簇大小：85 个 = 1 个来源；1 个 = 2 个来源
簇层级：86 个全部 auto
```

因此，像 EMM、GoInsight、Merchant System 下本来应由产品/能力/流程组织的多篇页面，仍以来源文件为粒度进入 S4。S2 的 `topic_id`（`cluster.py:59-61`）只是来源 ID 集合的哈希，不是语义主题 ID。Task2 后续得到很多单页主题、碎片化分类和难读文件名，是这个粒度决定的直接结果。

另外，单来源簇的 `pair_scores` 为空，`min_pair=1.0`（`cluster.py:42-48`），只要 token 数不少于 3 就自动进入 `auto`。这使“每篇独立来源”天然成为最高置信路径，而不是待模型判断的候选主题；现有测试没有覆盖单来源簇是否应进入语义主题规划。

S3 的规则实现不是“模型不可用时的安全回退”，而是正式主路径。它只能回答“词面上是否达到阈值”，不能回答“这篇资料究竟属于哪个产品/能力/流程、是否应该更新哪个主题”。`test_phase0_digest.py:752-855` 的断言也只证明分数排序和边界值正确，不证明目标主题选择正确。

Task2 最终运行的单来源样例（`company-kb/_digest/runs/run-fdaa20ff11e74de2a2f89fc6af3f6050/s3/evolution-decisions.jsonl`）显示：iOS 日志来源因 Jaccard `0.645161` 选中一个 iOS capability 页，其余四个候选分数仅约 `0.08`；这种路由是词面阈值产生的 `revise`，不是对“日志汇总”与“产品能力”关系的语义判断。若页面已有通用词，规则也可能把新资料写入错误主题。

## 现有测试覆盖了什么、没有覆盖什么

已有测试能证明：

- S1–S4 trace artifact 连续存在、重复和空壳被过滤（`test_phase0_digest.py:414-479`）。
- S2 低置信簇进入队列（`:689-710`）。
- S3 top-k、三种 action、阈值边界和候选分数一致（`:713-855`）。
- Task2 全量离线运行保留 claim 签名、页长和来源链接（`test_task2_corpus_regression.py:71-116`）。

但没有测试：

1. 同一产品/能力的多来源是否被组织成一个可读主题，而不是每篇一个主题。
2. 跨产品同名词、版本更新、流程与背景说明是否被错误合并。
3. 标题/H1/来源 metadata/Confluence 层级是否参与 S2/S3 决策。
4. 读者从 Home 找到目标知识所需时间、点击数、误分类率和主题完整性。
5. `needs_review` 是否真的阻止高风险错误写回；当前 S3 对其仍能继续规则路由。

`test_task2_corpus_regression.py:90-110` 的 `len(category_id)>1`、`other <=20%`、页长和链接检查，只是结构存在性门禁，不是语义质量门禁。它无法阻止“分类很多但每类内容不对”“标题可生成但不可读”这类用户实际感知的问题。

## 对知识质量的直接解释

1. **主题粒度错**：S2 只做来源间相似去重，不做产品/领域/能力主题建模；86 个簇几乎等于 86 个输入来源。
2. **路由依据弱**：S3 用全文词面分数和固定阈值选目标，不能识别上下文关系、版本关系、父子能力关系。
3. **质量门禁窄**：S1 能拒绝空壳，但不能拒绝“有内容、无结构、模板噪声高”的页面；下游会把噪声当知识。
4. **设计与验收错位**：原方案把“去重/增量合并”写得很细，却没有把“读者知识地图、主题边界、主题内结构、可读性”定义成 S1–S3 的硬输出和验收。因此代码可以通过所有现有测试，同时生成用户无法阅读的结果。

## 修复方向（供主任务汇总）

- 将“去重簇”和“读者主题”分成两个明确阶段：S2 保留防误合并的 source cluster；新增一个全量主题规划步骤，使用来源路径、标题/H1、产品实体、章节意图和 embedding/LLM 结合生成稳定主题图。
- S3 不再直接用 `len(selected)` 决定 revise/merge；先输出候选证据，再由受控的语义路由器给出目标主题、理由、置信度和冲突标记，低置信只进队列。
- 建立可持久化的 KB 主题/产品索引（不只是页面全文 embedding），让新来源能关联既有产品、能力、流程和版本主题。
- S1 增加正文结构化归一和噪声质量分数：保留标题层级、表格、代码、附件引用和来源路径；识别模板导航、重复 footer、无正文页面，并在进入 S2 前标记。
- 新验收必须包含 CompanyBrain 风格的读者任务：从 Home 找“某产品某能力”、打开主题页回答“是什么/怎么用/限制/版本/来源”，记录误分类、点击数、阅读时间和主题完整性；Claim 无损只能作为底线，不能作为质量结论。
